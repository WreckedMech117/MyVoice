## What Went Well

1. **Producer/consumer/cancel/dispatcher decomposition was clean.** Stories 16.3 (producer), 16.4 (consumer), 16.5 (cancel), 16.6 (dispatcher) decomposed the streaming pipeline into four independently-testable units. Each story shipped with explicit "what's NOT done" handoff blocks naming the next story's responsibility verbatim — Story 16.3 named the streamer's queue + cancel-event public surface for 16.4 to consume; 16.4 named the worker's `decode_fn` adapter shape for 16.6 to compose; 16.5 named the cancel-chain ordering for 16.6 to preserve. **Zero rework** — when 16.6 composed the surfaces, the call sites matched the predicted shapes byte-for-byte. The intent-driven architecture's interface decisions (P-5/P-6/P-7/D-10/D-11) did the design work upfront so the implementation collapsed to mechanical assembly.

2. **The trip-wire pattern from Story 16.1 paid off four times.** `tests/test_qwen_tts_internals.py` started at 3 trip-wires (Story 16.1: `Qwen3TTSModel` + `VoiceClonePromptItem` + 5-callable-method surface) and grew each story as new load-bearing imports landed: +1 in 16.3 (`transformers.generation.streamers.BaseStreamer`), +1 in 16.4 (`Qwen3TTSTokenizerV1Model.decode`), +1 in 16.8 (Path A talker hook target). Each addition was additive (~30 lines per pin) and the per-story documentation pattern was identical: name the symbol, name the call sites, name the failure-mode upgrade workflow. **The pattern holds up well** — in a future qwen-tts pin bump, this is the canonical "what to update first" file. Worth promoting to the project's `CLAUDE.md` as the "third-party private-surface trip-wire" pattern.

3. **The empirical-validation harness DID its job — twice.** Story 16.7's `scripts/validate_streaming_default.py` was the only mechanism that surfaced the two failures gating the streaming-default flip: (1) **TRUE_STREAM was structurally silent** — Story 16.6 wired everything but the talker hook was wrong, so empty chunks landed; the harness's empty-chunks regression guard caught this on the very first run on RTX 5090. (2) **SENTENCE_STREAM exceeded NFR1** by 9.07× — also caught by the same harness. Without the harness, both bugs would have shipped. **Empirical gates aren't ceremony — they're the actual safety net** when the architecture's projections (NFR1's "~1.5–1.8s estimated") don't survive contact with the real model + real hardware. Story 16.7 + 16.8 + 16.9 are a textbook example of a measurement-driven verification loop closing on real hardware.

4. **Latent infrastructure shipped first; activation came after — fourth epic running.** Stories 16.1-16.5 each shipped components with NO production caller until Story 16.6 wired everything together. The "inert-then-activate" pattern from Epics 11→13 (`saveable_session_changed`), Epic 12→13 (`_on_playback_queue_depth_changed` placeholder slot), Epic 14 (saveable lifecycle), Epic 15 (Clear Comms config snapshot) is now load-bearing across **four** epics. Each Story 16.X's "net-zero behavior change" claim was verifiable by `git diff` showing zero changes to existing call sites. This pattern is the project's structural answer to "how do solo-dev epics avoid mid-implementation rewrites" — the latent surface forces interface decisions upfront, before the consumer can muddy them with implementation details.

5. **Story 16.8's Path A talker-patch pivot was a genuine architectural improvement.** Story 16.8 entered with two candidate paths: Path A (forward-hook on `model.model.generate(streamer=...)`) vs Path B (literal preprocessing replication on `Qwen3TTSForConditionalGeneration.generate`). Initial implementation aimed at Path A via talker-patch but encountered a signature-preservation issue — qwen-tts 0.0.4's `Qwen3TTSForConditionalGeneration.generate` calls `self.talker.generate(...)` with positional + keyword arguments that varied across MyVoice's three generation modes (CUSTOM_VOICE / VOICE_DESIGN / BASE). Mid-implementation pivot to Path A via **forward-hook on `Qwen3Talker.forward`** instead — same intent, different attachment point, cleaner signature preservation. The pivot required a Story 16.8 Change Log #6 amendment but didn't require a story-creation rerun. **Lesson: when an implementation hits an architecture constraint mid-story, document the pivot in the Change Log and amend the AC text inline rather than restarting the story workflow.** The post-pivot Path A implementation is what shipped; Path B was never built (and Story 16.7's "TRUE_STREAM still fails" path-divergence verdict invalidated it).

6. **Code-review iteration to fixed point continued and caught real bugs four times.** Story 16.4's H1 was a **production-runtime bug**: `metrics.record('decode_error', repr(exc), ...)` would have raised `TypeError` from inside the worker's except block (real `metrics.record` validates `value` to `int|float`); the worker would have died mid-cancel-handler, never posting `('cancel', sid)`, leaving the session stuck in GENERATING. The bug was masked in tests by a fake recording sink that didn't validate. **Without code review, this would have shipped.** Story 16.6's C1 (orphaned `StreamingSettingsPanel` — tested in isolation but never wired into `SettingsDialog`) was caught the same way. Story 16.6's C2 ("subtask checkboxes marked `[x]` but tests didn't exist") forced the missing tests into existence. Story 16.9's M1 (label conflation in load-bearing tables — first_chunk vs generate_seconds) was caught in the eight-finding code-review pass after the empirical work shipped. **The "regression test must mirror the exact bug class" rule** (`memory/code_review_regression_test_exact_class.md`) was applied uniformly: Story 16.2's H2 split a tautological assertion into two tests; Story 16.4's H1 added a test using the real `metrics.record`; Story 16.6's M2 added two regression tests covering the truncation-with/without-suffix cases.

7. **Story 16.9's outcome (c) — pure contract revision — held up under empirical scrutiny.** AC #3 explicitly named contract revision as one of three legitimate outcomes; the dev agent didn't default to outcome (a) "implementation fix" when the data pointed elsewhere. The story-creation workflow's adversarial self-review (see Story 16.9 Change Log #2 — the H1 fix correcting `model_type` vs `quality_tier` confusion) prevented Hypothesis (b) from being measured wrong (would have used `QwenModelType.BASE` which is a *generation mode*, not a *model size* — the actual lever is `ModelRegistry.quality_tier` via `tier_override`). Without that pre-implementation correction, the small-tier comparison run would have produced silently-wrong data or a `ValueError`. **The story-creation review pass earns its keep when it catches a fabricated-symbol-path bug before the dev agent runs.**

## What Could Have Gone Better

1. **Story 16.6's CRITICAL findings were "marked as done but not actually done."** Two subtasks (7.4 + 7.6) were marked `[x]` in the dev cycle but the corresponding test files did not exist. The code-review pass found them via the "verify each [x] task" audit. The fix added the missing tests (renaming 7.4 because the literal "cancel before talker_thread.start()" was structurally untestable; the test exercises the next-closest realistic timing). **Lesson: a marked checkbox is a CLAIM about a code change, not the change itself.** When the workflow says "verify each [x] task by searching for evidence", that step is load-bearing. Add to the dev-cycle pre-commit checklist: `grep` the test file for the named test before marking the subtask `[x]`.

2. **Story 16.9's table-label conflation across three load-bearing artifacts went undetected through the dev cycle.** The "GPU SENTENCE_STREAM short" row in the report (§3.1), routing artifact (§2.1), and architecture amendment (empirical-contradiction table) all labeled the cited 4.18s as "first_chunk p95" when the number actually corresponds to `generate_seconds` p95 at n=17 (steady-state, excludes one-off cold model_load contribution). The bug was caught by the post-commit code-review pass and patched with explanatory footnotes rather than re-running the analysis. **Lesson: when a CSV has multiple latency columns whose values diverge only on a single edge case (s-001 warmup), document column-source explicitly in every table caption.** Cheap to do at table-drafting time; costs an explanatory-footnote retrofit at code-review time.

3. **Story 16.9's AC #4 / Subtask 6.4 "no fallback occurrences (D-9 / NFR12 invariant verified)" was empirically vacuous and went undetected through the dev cycle.** The harness uses `service._generate_streaming(request)` direct dispatch when `--mode-override sentence_stream` is set, bypassing `_dispatch_by_streaming_mode` (the metric-emitting public path). `_classify_dispatched_mode` therefore falls through to "the requested mode IS what dispatched" because `metric_recorder.last_streaming_mode is None` for every row. The AC was satisfied **by construction**, not by empirical observation. The harness's docstring at lines 484-501 acknowledged the bypass, but the AC text + Completion Notes still credited Story 16.9 with "verifying the invariant". Caught by code-review M2; softened in three places after the fact. **Lesson: when an AC names "verified by empirical observation", trace the claim through the actual dispatch path before drafting the AC.** The verification mechanism was wrong, even though the verdict was right (D-9 / NFR12 *is* upheld in production — by `tests/unit/services/test_qwen_tts_service_dispatch.py`, not by Story 16.9's harness runs).

4. **Story 16.9's stakeholder sign-off path deviated from AC #3 literal text.** AC #3 outcome (c) requires "routed through `/bmad-bmm-correct-course` for stakeholder sign-off BEFORE the merge". Actual path: routing went through `/bmad-bmm-dev-story`'s embedded `AskUserQuestion` prompt during the dev cycle. For solo-dev with Commander as sole stakeholder, the spirit (written, committed sign-off artifact alongside the architecture amendment) is preserved, but the literal AC text was not followed. The routing artifact `16-9-correct-course-nfr1-revision.md` exists and captures the same content, but the workflow invocation was different. **Lesson: when an AC names a specific workflow (`/bmad-bmm-correct-course`), use that workflow OR explicitly amend the AC at story-creation time** to allow the substitution. Don't substitute silently and disclose only in a post-commit code-review pass. Caught as M3.

5. **Story 16.4's H1 (decode_error metric TypeError in production) was masked by a too-permissive test fake.** The `_RecordingMetrics` fake's `__call__(self, name, value, **tags)` accepted any value type, including `repr(exc)` strings. The real `metrics.record` validates `value` to `int|float`. The test passed; production would have raised `TypeError` from inside the worker's except block, killing the cancel-post path. The code-review fix used the **real** `metrics.record` + `add_listener` for the H1 regression test, not the fake. **Lesson: regression tests for production-runtime bugs must use the real production object, not a permissive fake** — the fake's permissiveness IS the masking mechanism. This is now a third epic with a "fake masked the real bug" finding (Epic 13's M3, Epic 15's H1, Epic 16.4's H1). Worth promoting to a named pattern: when a test fake is more permissive than the production object it doubles, document it inline AND route the regression test through the real object.

6. **Story 16.9's `architecture-optimization-pass.md` "first git commit" status was hidden by the File List label "Modified".** The file was previously gitignored (`.gitignore` line 146 ignores all of `_bmad-output/`); Story 16.9's commit at `0953875` is its first git commit (`+976 / -0` stat). The substantive amendments (NFR1 cell line-802 pointer + new sub-section at line 819) are real edits to the local file but **cannot be seen as a git diff**. Reviewers who read the diff see a 976-line file blob, not a 2-place edit. Caught as L2; relabeled "Created (force-added; first git commit of file)" with a note. **Lesson: when force-adding a previously-gitignored file, label it as a Created artifact in the File List, not Modified — even when the substantive change is an edit.** Future story authors should grep `git log --follow <path>` before classifying an artifact as Modified vs Created in the File List.

7. **Multi-pass code reviews continued — Stories 16.6 and 16.9 each had two full review passes.** Story 16.6's first pass found 2 CRITICAL + 3 HIGH + 4 MEDIUM; the second pass found NEW issues the first missed. Story 16.9's adversarial self-review caught the `model_type` vs `quality_tier` confusion BEFORE implementation. The post-implementation code-review pass found 5 more findings (3 MEDIUM + 2 LOW). **Lesson: for stories with empirical / data-heavy deliverables, schedule TWO review passes: one at story-creation time (against the AC text and harness logic) and one at code-review time (against the data and the load-bearing tables).** Story 16.6's first pass found C1 (orphaned `StreamingSettingsPanel`) only because the second-pass reviewer (code-review workflow) compared the panel test file against the dialog test file and noticed the dialog tests didn't construct the panel. Cheap pattern: when a UI widget has its own test file, the parent dialog must have a test file naming it.

## Key Insights

1. **Empirical validation is not optional for dispatch / hardware / model-tier decisions.** The architecture's NFR1 projection (`~1.5–1.8s estimated`) was authored before empirical data on RTX 5090 + qwen-tts 0.0.4 was available. The empirical p95 is **9.07× over** that projection. Story 16.9 confirmed via phase-decomposition profiling that `_generate_sync` (the qwen-tts wrapper invocation) accounts for ≥99% of first-chunk wallclock — the bottleneck is upstream, not in MyVoice. The story-creation hypothesis (b) "0.6B small tier is faster" was **falsified with reversal**: the smaller model is ~2× SLOWER on Blackwell, the opposite of the prediction. **Without empirical measurement, four out of four design assumptions in NFR1's authoring would have been wrong on the actual hardware.** The harness is the project's primary epistemic mechanism for any future "is this architecturally sound on real hardware" decision.

2. **The "outcome (c) is not a failure mode" framing is a critical structural escape valve.** Story 16.9's AC #3 explicitly named contract revision as a legitimate verdict — not a fallback after implementation fails, but a peer outcome. The data + framing combined to let the dev agent ship **zero production code** while still closing the story by amending the contract. **For future stories with empirical-investigation scope, name contract-revision as an explicit ACoutcome at draft time** so the dev agent doesn't default to "make the implementation conform to the projection". This is the second time this framing has paid off (Story 14's saveable lifecycle had a similar branch where the contract was tightened rather than the implementation being expanded). Worth promoting to a story-template clause: "if the architecture-projected behavior is empirically wrong, amending the architecture is a valid AC outcome, not a story-failure".

3. **"Net-zero behavior change for users" is a verifiable claim per story.** Stories 16.1-16.5 each shipped with the explicit claim "no production code path consumes the new module yet — Story 16.X will wire it". The claim was verifiable by `git diff` showing zero changes to existing call sites and by the test suite showing zero new tests on existing surfaces. **The claim's verifiability — not just its existence — is what makes the latent-infrastructure pattern safe.** A non-verifiable claim ("we'll add the consumer in the next sprint, trust me") is a debt accelerator; a verifiable claim ("the consumer is Story 16.6, here's the file path") is a structural commitment. Worth carrying forward to any future epic that ships a producer/consumer split.

4. **`tests/test_qwen_tts_internals.py` is now the project's third-party-pin instrument.** Five trip-wires across Stories 16.1, 16.3, 16.4, 16.8 fence MyVoice's load-bearing imports from qwen-tts (4 trip-wires) and transformers (1 trip-wire). Bumping the qwen-tts pin in a future story is now a 3-step workflow: (1) read the upstream diff, (2) update `requirements.txt:21` + `build_tools/requirements-production.txt:54`, (3) run `pytest tests/test_qwen_tts_internals.py -v`. If green, ship the bump; if red, the failure message names the missing symbol(s) and their call sites in `src/myvoice/services/qwen_tts_service.py`. **The trip-wire test is the canonical "what to update first" file in any pin-bump story.** This is the structural answer to D-12's "import-attribute trip-wire" intent.

5. **Story 16.6's dispatch fork is the architectural pivot of the V2 streaming track.** Before Story 16.6, `QwenTTSService.generate()` had two paths: BATCH (default) and inline SENTENCE_STREAM (legacy). After Story 16.6, every public `generate*()` entry point routes through `_dispatch_by_streaming_mode(request, _resolve_streaming_mode())` which fans into a three-mode chain (TRUE_STREAM → SENTENCE_STREAM → BATCH). The fork is metric-instrumented (`streaming_mode` per attempt + `streaming_mode_fallback` per transition) and is the canonical observability surface for any future streaming-related question ("which mode did this user actually run?", "how often did fallback fire?"). **For any future Phase 6+ feature that touches dispatch, the metric is the source of truth, not the AppSettings field.** AppSettings stores the user's intent; the metric stores what actually ran.

6. **Three-day burn rate for a 9-story epic was sustainable but only because of preceding-epic discipline.** Stories 16.1 + 16.2 landed 2026-05-06; Stories 16.3-16.6 landed 2026-05-07; Stories 16.7-16.9 landed 2026-05-08. The three-day cadence held because: (a) the architecture's interface decisions (P-5/P-6/P-7/D-7/D-9/D-10/D-11) had already done the design work; (b) the latent-infrastructure pattern from Epic 11→13→14→15 was already established; (c) the trip-wire pattern from Story 16.1 generalized cleanly; (d) the code-review workflow caught real bugs at the right time. **Velocity is a downstream effect of design discipline — not the goal of design discipline.** This is the second three-day epic in a row (Epic 15 was a one-day epic; Epic 14 was multi-day). Worth tracking as a metric: post-Phase-1 epics have been ~1-3 days each; pre-Phase-1 epics (V1 baseline + voice-design archive) took weeks. The crossing-point was Phase 1's session-foundation discipline.

7. **`_bmad-output/planning-artifacts/architecture-optimization-pass.md` is now under git tracking.** Story 16.9 force-added the file as part of the NFR1 amendment commit (since `_bmad-output/` is gitignored, the file was previously local-only). Going forward, architecture amendments are diff-able. **Future architecture amendments should follow the two-place edit pattern** (inline pointer in the affected NFR/FR cell + new prose sub-section after the table) and be committed via `git add -f`. The Story 16.9 amendment is the canonical example. The Document Maintenance section (if present) should log the amendment per the existing convention.

## Significant Discoveries Affecting the "Streaming Default Ramp" follow-up story

**Epic 16 closes the latency-contract dimension of the streaming-default flag flip but leaves the perceptual-quality dimension open.** The "streaming default ramp" story (not yet drafted; see memory entry `epic16_streaming_blocked.md`) is the natural follow-up. Before drafting that story, consider the following discoveries:

1. **The flag itself is already in place.** `streaming_mode.py:54-56` returns `TRUE_STREAM` when `torch.cuda.is_available()` is True. `AppSettings.streaming_mode_override = None` (the default) defers to the hardware probe. **A GPU user with a fresh install today will hit TRUE_STREAM the moment the flag is flipped** — and that "flip" is an empty operation because the resolver already returns TRUE_STREAM. The actual change for the ramp story is **removing any UI-level safety net that pins users to SENTENCE_STREAM by default** (none exists currently — the Settings UI's "Streaming Mode" combobox defaults to "Auto" which delegates to the probe). So the ramp story is primarily about the **perceptual audition gate**, not the flag.

2. **The multi-listener perceptual A/B audition is the singular remaining prerequisite.** Story 16.7 AC #2 deferred this protocol after Story 16.7's empirical run found TRUE_STREAM was structurally silent. Story 16.8 partially exercised the audition (Commander solo, 2026-05-07) for the catastrophic-failure dimension only — i.e., does TRUE_STREAM produce audible speech at all? It does. The full audition (≥3 listeners, A/B paired comparison against SENTENCE_STREAM on the perceptual-difficult subset of the input set) is what the ramp story owns.
